# 团队代码开发规范

适用范围：本项目的后端、前端、内容生成、配音、数字人、集成与发布模块，以及相关脚本、配置和文档。供开发者、评审者及 AI 编码助手共同使用。

本文规定协作方式和新增代码的要求，不代表所有业务能力已经实现。现有实现逐步随相关任务完善，不为符合规范而夹带无关重构。Codex 操作还须遵守根目录 [AGENTS.md](../AGENTS.md)。

执行口径：带“必须”“禁止”“不得”的条款是交付约束；“建议”“推荐”“优先”允许根据任务说明取舍，其余条款作为默认约定。按改动范围应用，不要求小改动额外编写完整方案，也不要求每个 PR 涉及所有模块。本文不另行改变技术框架的职责分配或接口协议；发现冲突时由相关负责人澄清并同步文档。

## 1. 开发前明确交付

- 一个任务解决一个明确问题，写清输入、输出、验收条件、负责人和受影响模块。复杂任务在 `docs/` 中记录方案，再开始实现。
- 按 [CONTEXT.md](../CONTEXT.md) 使用领域术语，区分生产任务、模块作业、最终配音、口型视频、成片和发布结果。
- 功能范围以 [技术框架](技术框架.md) 为依据；首版顺序打通单条生产链路，不附带多任务调度、自动选题或字幕功能。
- 开工前阅读相关代码、测试和接口文档，确认已有能力，优先复用现有契约和工具。
- 涉及公共接口、依赖、数据库结构或启动脚本时，在任务或 PR 中提前说明影响，并请相关负责人参与评审。

## 2. 分工与模块边界

| 模块 | 主要职责 | 交付要求 |
| --- | --- | --- |
| 第 1 人：内容生成 | 写稿、检查、改稿及文本模型适配 | 最终口播稿、发布标题、话题标签 |
| 第 2 人：配音 | TTS、音色、发音与停顿、音频规格 | 最终配音及实测媒体信息 |
| 第 3 人：数字人 | 人物资源接入、口型生成、视频规格 | 与最终配音对应的口型视频及对齐信息 |
| 第 4 人：集成与发布 | API、Worker、状态持久化、合成、发布规则及结果查询 | 可播放成片、可追踪状态和真实发布结果 |

- 前三个模块通过本地 HTTP 向 Worker 提供能力，不互相串联，不直接执行抖音发布。
- 模型、供应商 SDK 和内部实现由对应模块封装；调用方只依赖接口契约，不直接读取其他模块内部数据库或导入其业务实现。
- 口型动作不匹配交由数字人模块处理；音轨整体偏移、封装与成片验证由集成模块处理。
- 人物形象的维护、核对与选定由专人负责，具体人员尚未指定；第 3 人负责的资源接入不等同于承担全部人物管理职责。
- 前端页面、人物管理等未明确到人的工作，在任务开始时指定开发和验收负责人，不从上述分工表自行推定归属。
- 公共契约、资产规则和共享配置由提出变更者与受影响模块共同确认。负责人不是代码独占者，跨模块修改必须说明影响并邀请对应负责人评审。
- 目录位置参照 [项目目录](项目目录.md)。预留目录不等于必须实现的功能，不仅为目录整齐新增空抽象层。

## 3. Git 协作流程

### 3.1 开始任务

先在项目根目录逐条执行，确认当前状态：

```powershell
git status --short
git branch --show-current
git remote -v
```

`main` 只保存已验证、可运行的代码，业务、配置和文档变更均通过短期任务分支提交。分支名称使用小写英文和连字符：

| 类型 | 示例 |
| --- | --- |
| 功能 | `feat/speech-service` |
| 修复 | `fix/task-recovery` |
| 文档 | `docs/development-guidelines` |
| 维护 | `chore/update-dependencies` |

工作区干净且在 `main` 时，从最新主分支开始。以下以配音任务为例；每条命令成功后才执行下一条：

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/speech-service
```

已在同一任务分支时继续使用。当前属于其他任务时，使用独立工作树隔离；有未提交修改时先确认归属，不自动暂存、覆盖或丢弃。不要创建长期人员分支或额外的 `develop` 分支。

### 3.2 提交和同步

- 一个提交只完成一件明确的事，不混入无关格式化、重构或他人修改。
- 提交信息使用 `<类型>: <中文说明>`，类型为 `feat`、`fix`、`docs`、`chore`、`refactor`、`test`。例如 `fix: 修复配音作业重复提交`。
- 先查看 `git diff`；未跟踪的新文件须单独检查内容。按具体路径 `git add`，避免使用 `git add .` 意外纳入运行数据。
- 提交前检查 `git diff --cached` 和 `git diff --cached --check`，确认没有凭据、本机路径、构建产物和其他任务文件。
- 首次推送使用 `git push -u origin <当前任务分支>`；尖括号内容须替换为实际分支名，后续只向该任务分支推送。
- 禁止强制推送或改写共享提交历史，不用 `git reset --hard`、`git clean -fd` 清理工作区。

同步前先提交当前任务已完成的修改，保持工作区干净，在任务分支上逐条执行：

```powershell
git fetch origin
git merge origin/main
```

冲突按双方意图解决，不直接用整份文件覆盖。解决后检查差异，重新执行受影响检查，再提交与推送。

### 3.3 PR 和合并

- 一个 PR 对应一个可独立评审的任务，说明问题、完成后的行为、验证结果及未完成部分。
- 至少另一名成员审批，相关检查通过后才可合并；公共接口变更应包含受影响模块负责人的评审。
- 尚未接入自动化 CI 时，在 PR 中记录本地检查命令、结果和对应提交号，由评审者核对；配置了 GitHub 必需检查后仍须等待其通过。本地验证不替代必需检查，也不表示已启用 CI。
- 推荐 **Squash and merge**。创建 PR 不代表允许合并；Codex 只有在用户明确要求且审批、检查满足时才执行合并。
- 合并后删除远程任务分支，更新本地 `main`，执行 `git fetch --prune`。本地优先用 `git branch -d`；Squash 导致删除被拒绝时，先核实 PR 已合并、无未推送提交、工作区干净，才考虑 `git branch -D`。
- 建议管理员为 `main` 配置必须 PR、至少一人审批、相关检查通过及禁止强推的保护规则。文档约定不等于 GitHub 已启用保护。

## 4. 通用编码要求

- 注释、文档和面向用户的错误说明使用中文；程序标识符、命令和标准名称保留英文。文件使用 UTF-8，沿用所在文件的缩进和换行风格。
- 名称体现业务含义和单位，例如 `task_id`、`job_id`、`duration_ms`、`timeout_seconds`，避免含糊的 `data1`、`temp2` 或同义词混用。
- 函数围绕一个职责组织，优先使用明确参数和返回值。出现重复业务规则时提取公共实现，不为尚不存在的需求设计通用框架。
- 注释解释业务约束、设计原因或边界，不逐行复述代码。临时方案注明原因和后续处理条件，不保留大段注释掉的旧实现。
- 边界处校验外部输入；内部使用明确类型传递数据，不靠隐式类型转换或拼接字符串传递复杂结构。
- 错误不得静默吞掉，不以空结果或假成功掩盖失败。捕获可处理的具体异常；兜底异常只在任务或请求边界处理，并记录可追踪原因。
- 日志包含适用的生产任务编号、模块作业编号、请求编号、阶段和耗时；不记录密钥、令牌、完整敏感请求或媒体内容。
- 引入依赖前确认现有工具能否满足需求，并说明用途；依赖清单与锁文件同时更新，不手工修改锁文件。

### 开闭原则

- 新增和修改代码必须遵循开闭原则（Open–Closed Principle，OCP）：对扩展开放，对修改关闭。针对已明确的变化点，通过稳定接口与新增实现扩展能力，尽量保持已验证的核心逻辑和现有调用方不变。
- 本项目新增文本模型、TTS 或数字人供应商时，优先新增符合现有契约的适配实现，在统一的配置或组装入口选择实现；避免在路由、Worker 和业务模块中散布供应商判断分支。
- 接口按实际职责定义，可使用 Python Protocol、TypeScript interface、函数注入或组合实现扩展，不强制采用继承，也不为尚未出现的变化创建插件框架或多层抽象。
- 开闭原则不禁止修复缺陷、调整配置或演进业务规则。现有接口无法表达已确认需求时，可以修改接口与核心逻辑，但必须说明影响，同步契约与相关文档，并按变更范围验证兼容性。
- 扩展功能时验证新增实现符合公共契约，并运行受影响的已有行为测试；评审重点检查是否能通过现有扩展点实现、是否出现重复分支，以及是否引入无实际需要的抽象。

## 5. Python 后端规范

- 集成后端和内容模块以 Python 3.11 为基线，使用 uv 管理依赖；配音、数字人需要独立模型环境时，由负责人提供依赖清单和可复现安装说明。
- 模块、函数和变量使用 `snake_case`，类使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`。新增公共函数与模块边界函数提供参数和返回类型标注。
- HTTP 请求、响应和配置优先使用现有 Pydantic 模型。公共传输模型位于 `backend/app/contracts/`，不在路由内重复定义相同契约。
- 路由负责接收、校验、调用业务逻辑和返回结果；供应商接入放在适配层，逐步避免把模型调用、SQL 和流程编排堆在路由函数中。
- 跨模块生产流程由集成模块的独立 Worker 编排，不依赖页面保持打开。前三个服务受理作业后异步执行并提供状态查询，内部采用进程、线程或其他执行方式由负责人按模型要求决定；不得把长时推理放在提交请求中等待完成，也不得在异步路由中直接执行阻塞操作。
- HTTP 调用设置超时并按协议处理重试。数据库操作使用参数化 SQL；幂等记录、作业建立及相关状态变更按业务原子性要求使用事务。
- 数据库结构变化提供版本化迁移和升级说明，说明已有数据如何保留及失败如何恢复；不通过删除本机数据库冒充迁移成功。
- 文件路径使用 `pathlib` 等标准工具。调用 FFmpeg 等进程使用参数列表、检查退出码并设置适当的超时，不把外部输入拼进 shell 命令。
- 遵循现有 Ruff 配置，不为消除检查错误而全局关闭规则；确需局部豁免时说明原因。

## 6. React / TypeScript 前端规范

- 使用 React 函数组件和 Hooks，保留 TypeScript `strict` 检查。组件和类型使用 `PascalCase`，函数、变量和 Hooks 使用 `camelCase`，自定义 Hook 以 `use` 开头。
- 页面放在 `frontend/src/pages/`，复用组件放在 `frontend/src/components/`。接口访问逻辑随着复用需要集中封装，避免组件各自复制地址、错误处理和轮询代码。
- HTTP JSON 字段遵循协议的 `snake_case`；若映射为前端字段，在 API 边界显式转换，不能只修改类型声明。
- 避免随意使用 `any`、非空断言或类型断言跳过校验。静态 TypeScript 类型不等于对服务端响应做了运行时校验。
- 表单包含必要的输入校验；异步页面区分加载、空结果、失败和成功，错误提供可理解的说明及适用的后续操作。
- 轮询在组件卸载、切换任务或进入终态时清理，处理过期请求，避免旧响应覆盖新任务状态。
- 按钮交互防止重复点击；后端仍须实现幂等，不能只依赖按钮禁用。页面不得根据轮询中断推断任务已失败或已取消。
- 优先复用 Ant Design 与已有样式，使用稳定列表 key，表单控件提供明确标签。界面状态以服务端业务结果为准，不把“已受理”显示为“已发布”。
- 模型及平台凭据只保留在服务端，不写入前端源码或 `VITE_*` 变量。

## 7. 接口、状态和媒体交接

接口语义以 [HTTP 接口协议](HTTP接口协议.md) 为依据；该协议当前仍待负责人评审。实现前确认适用版本，遇到模型、文档与实际行为不一致时先对齐，不自行猜测。公共模型及校验边界见 [公共数据契约](contracts/README.md)。

- Python 模块复用公共模型；其他语言可使用生成的 JSON Schema，并补齐文档要求但 Schema 未覆盖的跨字段和业务校验。
- 契约变更同时更新协议、模型、生成的 Schema、示例及测试，不手工编辑生成文件。删除字段、改变含义或增加必填请求字段时按协议升级主版本。
- 请求端拒绝未知字段，因此新增可选请求字段也需先更新接收方，再启用发送方；响应端新增字段则核对调用方能否忽略。PR 写明各模块采用的契约版本和升级顺序，不以“只是加字段”为由跳过兼容性确认。
- 明确区分可省略字段和可空字段，保留必填的 `null`；不要为统一序列化随意丢弃它们。
- 请求编号用于追踪，幂等键用于防重复。POST 超时后核实原请求，按协议使用相同请求体和相同幂等键重试，不自动换键重做。
- 区分 HTTP 请求失败与模块业务失败；`succeeded`、`failed` 为不可变终态。状态转移、幂等与重启恢复需要持久化校验，不能只依赖数据模型。
- 文件交接使用资产根目录下的相对路径，不返回开发者盘符路径。解析后检查实际路径仍在资产根目录内，包括符号链接或目录联接造成的越界。
- 文件完整写入并验证可读后才返回成功；核验摘要、大小和实际媒体信息，不只依赖扩展名。临时文件和最终产物分开，避免读取半成品。
- 首版媒体规格遵循协议的已确认基线；采样率兼容性和实际时长通过测量确认，不能以配置值代替实测结果。
- 口型视频和成片必须关联同一份最终配音。返工产生新作业和新产物，不覆盖仍被已完成任务引用的文件。
- 发布已提交、平台处理中、确认已发布及结果待核实分别记录。发布结果不明时先查询核实，不自动再次发布。

## 8. 配置、依赖与本机数据

- 安装与启动统一参考 [安装说明](installation.md) 和 [依赖与环境](依赖与环境.md)，不把个人电脑的安装位置写进共享源码。
- `.env` 仅在本机保存。新增或变更配置字段时同步更新 `.env.example` 和说明，中文注释说明用途、单位、默认值和是否必填，真实密钥留空。
- 配置通过统一入口读取和校验，供应商地址、模型 ID、服务端口、超时与资产根目录不散落在业务代码中。
- 集成后端和内容模块提交 `pyproject.toml` 与 `uv.lock`；前端提交 `package.json` 与 `package-lock.json`。使用锁文件安装，避免不同成员得到不同依赖版本。配音、数字人独立环境按所选工具提交可复现的依赖版本文件，并说明 Python、CUDA 等兼容要求，不强制迁入集成环境。
- 不提交虚拟环境、`node_modules`、构建产物、数据库、日志、模型权重和业务素材；新增运行数据类型时同步检查忽略规则。
- 不同测试运行和独立工作树隔离数据目录与服务端口；同一次联调中的 API 与 Worker 按设计共享集成数据库，四个模块按协议共享资产根目录。禁止不相关的开发实例误用同一份运行数据。使用标准启停脚本时，在各工作树本机 `.env` 中配置目录并通过 `-Port` 区分端口，不设置脚本明确拒绝的进程级 `VIDEO_DATA_DIR` 环境变量。

## 9. 验证与交付门槛

按改动范围执行检查，记录命令、结果和未覆盖范围。检查失败应修复或明确报告，不能省略失败项。

下列后端命令覆盖集成后端及公共契约；配音、数字人等独立服务还须运行自身的测试或自检，并在交接文档中给出命令与结果。仅运行集成端测试不能证明这些独立服务通过验证。

| 变更范围 | 必须完成 |
| --- | --- |
| 后端逻辑、配置读取 | pytest、Ruff；按影响补充正常、边界与失败场景 |
| 公共契约 | 后端检查、Schema 一致性检查、受影响模块兼容性确认 |
| 前端代码、构建配置 | TypeScript 与生产构建；受影响页面的交互验证 |
| 媒体工具、合成链路 | 相关媒体自检；真实链路改动还需对应真实素材验证 |
| 脚本 | 语法检查，以及受影响的安装、启停或验证行为 |
| 仅文档、注释 | 内容、链接、UTF-8 编码和差异空白检查 |

后端命令，在 `backend/` 执行：

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m ruff check app tests
```

公共模型有改动时，仍在 `backend/` 生成并核对 Schema：

```powershell
.venv/Scripts/python.exe -m app.contracts.schema
.venv/Scripts/python.exe -m app.contracts.schema --check
```

前端构建与差异检查，在项目根目录执行：

```powershell
npm.cmd --prefix frontend run build
git diff --check
```

媒体环境自检在按安装说明完成配置并启动 API、Worker 后，于项目根目录执行：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/verify.ps1
```

非默认端口在命令末尾添加对应参数，例如 `-Port 8766`，与启动端口保持一致。该脚本验证本机环境与自检成片，不证明真实模型生成或抖音发布已接通。

测试应验证对外行为和关键业务约束，优先覆盖重复提交、超时、服务失败、状态恢复、资产越界和产物不匹配等适用场景。普通自动化测试使用临时目录及替身服务，不依赖真实密钥、不产生收费请求或真实发布。真实联调单独记录服务版本、素材、步骤和结果。

当前前端已提供类型检查与构建脚本，尚无自动化测试脚本；构建通过不能替代浏览器交互验证，也不要记录未运行的前端测试为通过。

## 10. PR 与模块交接模板

以下模板可直接复制到 PR，按实际范围填写，不适用项注明原因：

简单文档或局部修复可精简为“问题与结果”“验证”两部分；存在兼容性、迁移或未完成事项时须保留对应说明。

```markdown
## 问题与结果

- 原来的问题或本次需求：
- 修改后的行为：
- 关联任务：

## 影响范围

- 涉及模块与需参与评审的负责人：
- 接口、配置、依赖或数据库变化：
- 兼容性、升级及恢复方式：

## 验证

- 已运行的命令与结果：
- 交互或联调步骤与结果：
- 未验证范围及原因：

## 未完成部分

- 剩余问题、影响和后续负责人；没有则填“无”：
```

模块交接还需提供启动命令、环境依赖、配置模板、服务地址、接口版本、健康或就绪检查方式、可复现请求与响应、资产目录约定和已知限制。示例不得含真实凭据。

评审者重点检查：是否符合需求与模块边界，接口是否兼容，异常和重试是否可靠，状态与产物是否可追踪，配置与凭据是否妥当，验证证据是否覆盖本次改动。只有代码写完、相关验证完成、文档同步且评审通过，才具备合并条件。
