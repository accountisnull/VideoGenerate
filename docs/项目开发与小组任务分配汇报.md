## 二、项目目标与总体方案

首版交付目标是：人工输入一个主题，自动生成口播稿、最终配音、口型视频和成片，经预设规则校验后提交抖音，并保存平台确认的发布结果。

```mermaid
flowchart LR
    A[人工输入主题与选择资源] --> B[程贺龙：内容生成与检查]
    B --> C[杨子祥：最终配音]
    C --> D[李宇昊：口型视频]
    C --> E[陈思锴：音画对齐与合成]
    D --> E
    E --> F[陈思锴：规则校验与发布核实]
```

上图是目标业务流程；实际调用由陈思锴的独立 Worker 统一编排，前三个服务通过本地 HTTP 提供能力，彼此不直接串联。

| 部分 | 已确定方案 | 作用 |
| --- | --- | --- |
| 页面 | React、TypeScript、Vite、Ant Design | 输入主题、维护与选择人物、查看任务、预览成片及发布结果 |
| 集成后端 | Python 3.11、FastAPI | 业务接口、资源校验与任务管理 |
| 执行流程 | 独立 Worker，首版顺序执行单条链路 | 页面关闭后继续执行，保存阶段结果与恢复信息 |
| 数据与文件 | SQLite、本地共享资产目录 | 保存业务状态，交接配音、视频与成片 |
| 内容生成 | deepagents、Skills、百炼文本 API | 写稿、检查、改稿；具体模型通过配置选择 |
| 配音与数字人 | 对应负责人选型并提供 HTTP 服务 | 允许使用独立模型环境，按公共契约交付 |
| 媒体处理 | FFmpeg、ffprobe | 测量、对齐、合成和成片验证 |

首版只打通一条真实链路，不做批量并发生产、自动选题、字幕、发布后的运营监控或策略优化。发布由预设规则控制，不增加逐条人工点击确认的业务环节。

## 五、开发顺序与阶段安排

采用“先统一接口、再并行实现、随后真实联调”的顺序。下表按完成条件推进，不预设未经成员确认的工期；最终发布日期取决于真实模型兼容性和平台权限。

| 阶段 | 主要工作与并行关系 | 负责人 | 完成标志 |
| --- | --- | --- | --- |
| M0：基线与职责确认 | 评审 HTTP 草案；登记服务地址、配置档和资源；确认前端、人物、规则负责人；各成员给出预计日期 | 全组，陈思锴组织 | 每个模块知道接收什么、交付什么、如何验收，待定事项有负责人 |
| M1：模块可独立运行 | 程贺龙、杨子祥、李宇昊并行实现真实服务；陈思锴实现 Worker 并用替身验证调用与恢复；前端按契约开发 | 四人并行 | 各服务可独立提交、查询并交付一份真实结果；调用、失败和重启场景有证据 |
| M2：真实生成与成片 | 按内容→配音→数字人→合成逐段接通，用同一份最终配音贯穿视频与成片 | 陈思锴牵头，各模块修复本段问题 | 一次主题输入得到可播放真实 MP4，保存完整任务、作业及产物关联 |
| M3：真实发布闭环 | 接入预设规则、平台提交和结果核实；测试结果不明时的查询处理 | 陈思锴、规则维护人、账号持有人 | 一条真实视频取得平台确认的发布结果，并保存核对依据 |
| M4：交接验收 | 回归关键失败恢复；核对安装、配置和操作说明；完成成员评审 | 全组 | 其他成员可按文档复现，已验证代码经审批进入主分支 |

**平台权限核验从 M0 就并行开始，不等成片完成后再申请。** 若权限暂不可用，仍推进 M1、M2，并将 M2 明确标为“真实生成阶段完成”；首版完整交付仍需 M3 的真实发布结果。

模型样例也可提前交接：杨子祥用固定口播稿验证 TTS，李宇昊使用杨子祥提供的样例配音验证口型；这些用于独立开发和兼容性检查，M2 必须再使用同一生产任务的真实上游结果联调。

## 六、接口交接与协作方式

每个模块交接时提供同一套资料：启动命令、环境依赖、配置模板、服务地址、契约版本、就绪检查方式、正常与失败请求响应、真实样例产物、已知限制和验证结果。密钥只在本机服务端保存。

联调遵循以下共同约定：

- 耗时作业先返回编号，通过查询取得状态；任务和幂等信息持久化，超时先核实原请求，不更换键盲目重做。
- 接口传资产根目录内的相对路径，文件完整写入后交付，并带上摘要、大小和实测媒体信息。
- 首版配音基线为 WAV／PCM 16 位单声道，优先验证 24 kHz 并尊重 TTS 原生采样率；视频基线为 720×1280、恒定 25 fps、H.264／MP4。具体兼容性按 [协议媒体规格](HTTP接口协议.md#首版媒体规格已确认)实测。
- 能力交付须区分“替身通过”“真实模块通过”“真实整链通过”；自动化测试数量不替代音质、嘴型和最终发布验收。

全员使用 Codex 时，先读 [AGENTS.md](../AGENTS.md) 和 [开发规范](开发规范.md)，遵循开闭原则和公共契约。每位成员在自己的机器上使用一个项目工作目录，各任务使用短期分支；未经明确许可不新增工作树、不推送。至少另一名成员审批 PR，AI 自检不能代替成员审批。

建议每日用简短同步说明“已交付证据、下一步、阻塞、需要谁配合”，出现接口字段、媒体规格或服务能力变化时及时通知受影响成员并更新文档。交付按验收证据判断，不能只说“代码写完了”。

## 九、三分钟口头汇报稿

我们这个项目首版的目标，是从人工输入一个主题开始，自动完成口播稿、配音、数字人口型视频和最终成片，再按预设规则发布到抖音，并拿到平台确认的结果。首版先打通一条真实链路，不做批量并发、自动选题或字幕。

目前技术路线和模块边界已经确定，采用 Python 和 FastAPI 做后端，React 做页面，通过独立 Worker 串联各模块，SQLite 保存任务状态，本地共享目录交接媒体。基础环境、自检功能和公共数据契约已经有了；生产任务存储、创建和查询接口也已在本地实现。最新验收记录是 219 项测试通过，但这些主要验证接口和状态逻辑，真实生成服务、生产 Worker 和抖音发布还需要继续接入，本地新实现也尚未完成团队共享。

分工上，程贺龙负责内容生成、检查和发布标题标签；杨子祥负责 TTS 与最终配音；李宇昊负责人物资源接入和口型视频；我负责状态、流程集成、音画合成以及发布结果核实。每个人交付的都应是能启动、能提交和查询、有真实样例与验证记录的模块。

下一步建议先统一接口和资源配置，然后四个人并行推进：三个生成模块各自提供真实服务，我同步实现 Worker，先用替身验证串联和恢复，再逐段替换为真实服务。杨子祥和李宇昊要尽早交换配音样例验证兼容性，抖音权限也要现在开始核验，避免到成片完成后才发现无法发布。

今晚主要需要确定每位成员的交付日期，以及前端、人物维护、发布规则和账号授权配合人的归属。集成和发布的工作量比较集中，需要明确分担。大家统一按项目中的 Codex 约束开发，通过任务分支和成员评审协作，未经明确许可不自动推送。阶段验收以可运行的真实结果为准，最终以一条视频完成真实发布作为首版闭环。

## 十、汇报展示建议

可按六页组织：① 目标与业务流程；② 当前进展及边界；③ 四人职责与交付表；④ 阶段安排；⑤ 风险与未分配工作；⑥ 今晚需确认事项。

若现场演示，优先展示已验证的环境自检及接口测试证据。自检 MP4 明确标注“环境测试样片”；生产 API 默认未就绪时如实说明，不演示绕过就绪校验，也不把测试模拟的发布结果当作真实发布。
